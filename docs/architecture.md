# Архитектура

## Нагрузка

- **Верхняя граница из условия:** 100M голосов за ролик. Теоретический пик 100M RPS, если все проголосуют в одну секунду.
- **Реальный ориентир:** рекламный ролик Coinbase на Super Bowl 2022 — минута с одним QR-кодом, ~100M зрителей, за переход давали бесплатный биткоин. Результат: 20M заходов за минуту, и приложение упало. У опроса без приза отклик будет ниже.
- **Цель проектирования:** 20–30M голосов за ролик, пик — несколько миллионов RPS. Всплеск приходится на 10–20-ю секунду ролика.

Голос — это «+1 к счётчику». Порядок голосов неважен, итог может подождать минуту. Поэтому приём отделён от подсчёта.

## Схема

```
Телефон ──► CDN: страница + конфиг опроса (статика)
   │
   └─ голос ─► L4-балансировщик ─► сервисы приёма (без состояния)
                                        │ пачки, acks=all, партиция = hash(IP)
                                        ▼
                                  кластер Kafka (3 реплики)
                                        │
                                        ▼
                                  потребители (по партициям)
                                  дедупликация в памяти, итоги по вариантам
                                        │
                                        ▼
                     Postgres: опросы и итоги ◄── админка
```

1. **Страница.** Статический HTML+JS на CDN. Считает отпечаток браузера, хранит `voter_id` в cookie и localStorage. Отправляет голос через `fetch(..., {keepalive: true})`: запрос долетит, даже если вкладку сразу закрыли. В России Cloudflare замедляется провайдерами, поэтому для российской аудитории нужен российский CDN.
2. **Приём.** Узел без состояния:
   - собирает компактную запись ≈ 64 Б: опрос, вариант, время, IP, хэш отпечатка, `voter_id`;
   - копит записи в пачку несколько миллисекунд и отправляет её в Kafka;
   - отвечает `204` **только после подтверждения** Kafka.

   Масштабируется добавлением узлов.
3. **Очередь.** Кластер Kafka: 3 реплики, запись подтверждают минимум 2 (`acks=all`, `min.insync.replicas=2`). Партиция выбирается по хэшу IP.
4. **Потребители.** Каждый владеет своими партициями, а значит своими IP. Всё состояние дедупликации лежит в его памяти, общих счётчиков нет. Итоги по вариантам (засчитанные и все голоса) периодически записываются в Postgres с ключом «опрос + партиция». Подробности — в [architecture_deduplication.md](architecture_deduplication.md).
5. **Админка.** Создаёт опрос и публикует его конфиг на CDN. Показывает итоги: сумму строк по партициям, только агрегаты.

## Отказы

| Что упало | Что происходит |
|---|---|
| Узел приёма | Балансировщик убирает его из работы. Голоса, по которым узел не успел ответить, теряются: из закрытой вкладки повторить некому. Потеря ограничена одним узлом и долями секунды. |
| Брокер Kafka | Его партиции за секунды переходят к репликам. Подтверждённые записи не теряются. |
| Потребитель | Перечитывает свою партицию с начала опроса (минута данных) и перезаписывает свои итоги. Ничего не теряется и не засчитывается дважды. |

Сырые голоса лежат в Kafka весь срок хранения. Из них можно считать статистику и пересчитать итоги.

## Мощности

Узлы приёма и потребители не хранят состояния и масштабируются линейно. Цену определяют замеры на одно ядро (см. README):

| | 5M RPS | 100M RPS |
|---|---|---|
| TLS-рукопожатия (≈ 5–7 тыс./с на ядро) | ~800 ядер | ~15–20 тыс. ядер |
| Приём и запись в Kafka (X голосов/с на ядро) | 5M / X ядер | 100M / X ядер |
| Сеть (≈ 5 КБ на голосующего) | ~200 Гбит/с | ~4 Тбит/с |
| Kafka (64 Б × 3 реплики) | ~1 ГБ/с, минимальный кластер | ~20 ГБ/с, 5–10 брокеров |

**Время до итога** = число голосов / скорость потребителей. Хочешь итог быстрее — добавляешь потребителей и партиции.

При 100M RPS архитектура та же. Меняется только число узлов, это вопрос бюджета.

## Подготовка к эфиру

Время выхода ролика известно заранее, поэтому автомасштабирование, которое не успеет за секунды, не нужно:
- поднять мощности до эфира;
- прогреть балансировщики и CDN;
- прогнать нагрузочный тест на целевой пик;
- после эфира сократить мощности обратно.
