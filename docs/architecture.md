# Архитектура

## Нагрузка

- **Верхняя граница из условия:** 100M голосов за ролик.
- **Реальный ориентир:** рекламный ролик Coinbase на Super Bowl 2022. Минута с одним QR-кодом, ~100M зрителей, за переход давали бесплатный биткоин. Итог: 20M заходов за минуту, приложение упало. У опроса без приза отклик будет ниже.
- **Кривая во времени.** Реальных данных о ней нет, поэтому используем модель. Предполагаем, что половина голосов приходит между 10-й и 20-й секундой. Время реакции не бывает отрицательным и имеет длинный правый хвост, поэтому берём логнормальное распределение с медианой 14 с и σ = 0.5. Пик приходится на ~11-ю секунду: в эту секунду приходит 6.5% всех голосов.

| Голосов за ролик | Пик |
|---|---|
| 25M (цель проектирования) | ~1.6M RPS |
| 100M (проголосовали все) | ~6.5M RPS |

Голос — это «+1 к счётчику», а итог нужен после ролика, а не в реальном времени. Поэтому приём отделён от подсчёта, а итог считается один раз, после закрытия окна.

## Схема

```
Телефон ─► CDN: страница, конфиг опроса; /api проксируется к нам
                              │
                              ▼
          L4-балансировщик ─► приём (без состояния)
                              │ acks=all
                              ▼
          Kafka: votes_raw (ключ = voter_id)
                              │
                              ▼
          этап 1, потоковый: один голос на voter_id
                              │
                              ▼
          Kafka: votes_by_ip (ключ = HMAC(IP))
                              │
                              ▼
          этап 2, после окна: два прохода по партиции
                              │
                              ▼
          Postgres: опросы и итоги ◄── админка
```

1. **Страница.** Статика на CDN, API на том же домене: CDN проксирует `/api` к нам. Это даёт три вещи:
   - cookie остаётся своей, её пропускает Safari ITP;
   - нет CORS-preflight;
   - TLS завершается на CDN в соединении, открытом ещё при загрузке страницы.

   Для российской аудитории CDN нужен российский: Cloudflare в России замедляют провайдеры.

   Что делает страница:
   - генерирует `voter_id`, хранит его в cookie и localStorage и блокирует кнопку после голоса;
   - считает отпечаток (см. [architecture_deduplication.md](architecture_deduplication.md));
   - отправляет голос через `fetch(..., {keepalive: true})`, поэтому он долетает, даже если вкладку закрыли;
   - пока вкладка открыта, повторяет отправку с экспоненциальной задержкой и разбросом, с тем же `voter_id`.

2. **Приём.** Узел без состояния.
   - Опрос, варианты, окно и соль проверяет по кэшу активных опросов в памяти, без обращения к БД на каждый голос.
   - Собирает запись ≈ 100 Б: опрос, варианты (битовая маска, чтобы поддержать мультивыбор), время приёма, `HMAC(IP, секретная соль опроса)` (для IPv6 по префиксу `/64`), хэш отпечатка, `voter_id`. Сырой IP дальше приёма не уходит.
   - Настоящий IP клиента берёт из PROXY protocol или из `X-Forwarded-For`, но только от доверенных прокси.
   - Пишет пачками в Kafka и отвечает `204` **только после подтверждения**.
   - Если буфер продюсера переполнен, сразу отвечает `503`, и клиент повторит запрос.

3. **Kafka.**
   - 3 реплики, запись подтверждают минимум 2; реплики разнесены по зонам доступности.
   - Идемпотентный продюсер, сжатие lz4, явный partitioner (murmur2).
   - `delivery.timeout.ms` 2–5 с, в согласии с HTTP-таймаутом.
   - Число партиций фиксируется до опроса (64–128). Если его поменять во время опроса, голоса одного IP разъедутся по разным партициям.
   - Хранение — несколько дней, затем удаление.

4. **Этап 1, потоковый.** Партиции `votes_raw` разбиты по `voter_id`. Засчитывается первый голос каждого `voter_id` в порядке партиции, повторы уходят с пометкой. Смена Wi-Fi на LTE или VPN-сервера не даёт второго голоса. Уцелевшие голоса переписываются в `votes_by_ip`.

5. **Этап 2, после окна.** Партиции `votes_by_ip` разбиты по `HMAC(IP)`. Каждая партиция обрабатывается в два прохода (подробно — в документе о дедупликации). Итоги пишутся в Postgres строками вида (опрос, партиция, вариант, засчитано, всего, `last_offset`). Запись проходит, только если `last_offset` больше сохранённого, поэтому зависший старый потребитель не перезапишет свежий итог. Итог окончательный, когда все партиции дошли до последнего offset опроса.

6. **Админка.**
   - Создание опроса и его жизненный цикл: черновик → активен → закрыт. При активации конфиг публикуется на CDN.
   - Итоги: сумма строк по партициям, только агрегаты.
   - Во время эфира видна только цифра «голосов принято».
   - Вход по токену.

## Окно голосования

Окно = время ролика + допуск на задержку вещания: OTT и спутник отстают на 30–60 с. Время голоса ставит узел приёма, часы потребителей ни на что не влияют. Чем длиннее окно, тем больше повторов успевает накрутчик (см. `R` в документе о дедупликации).

## Отказы

| Что упало | Что происходит |
|---|---|
| Узел приёма | Балансировщик замечает это за секунды. Всё это время голоса, отправленные на узел, и неподтверждённые голоса в его буфере теряются, если вкладку уже закрыли. Из открытой вкладки клиент повторит отправку. |
| Брокер Kafka | Партиции за секунды переходят к репликам, подтверждённые записи не теряются. Пока идёт переключение, приём держит голоса в буфере; если буфер переполнен, отвечает `503` и клиент повторяет. |
| Зона доступности | Реплики в других зонах, кластер продолжает работу. |
| Потребитель | Состояние хранится на партицию, а не на потребителя. Новый владелец перечитывает партицию с начала опроса. Решения зависят только от содержимого партиции, поэтому итог совпадает до голоса. |

## Мощности

Узлы приёма и потребители не хранят состояния и масштабируются линейно. Цену определяют замеры на одно ядро (см. README).

| | 1.6M RPS | 6.5M RPS |
|---|---|---|
| CDN: страница ≤ 30 КБ | ~400 Гбит/с | ~1.6 Тбит/с — ёмкость согласуется с CDN заранее |
| Приём (X голосов/с на ядро; оценка для Python — 5–10 тыс.) | 1.6M / X ядер | 6.5M / X ядер |
| Сеть до нас (~1 КБ на голос) | ~13 Гбит/с | ~52 Гбит/с |
| Kafka (2 топика × 100 Б × 3 реплики) | ~1 ГБ/с, 3–6 брокеров | ~4 ГБ/с, 10–15 брокеров |

**Время до итога** ≈ число голосов / суммарная скорость потребителей × 2 прохода. Чтобы итог был быстрее, добавляем потребителей: партиций заложено с запасом.

## Подготовка к эфиру

Время выхода ролика известно заранее, поэтому на автомасштабирование, которое не успевает за секунды, не полагаемся:
- мощности поднимаем до эфира;
- прогреваем балансировщики и CDN;
- заранее прогоняем нагрузочный тест на целевой пик;
- после эфира ужимаем мощности.

## Вопросы к продукту

- **Показывать ли итоги в реальном времени.** Это вопрос честности, а не красоты: видимый лидер подталкивает голосовать за него. По умолчанию не показываем.
- **Повторы ролика в разных часовых поясах:** один опрос с несколькими окнами или отдельные опросы.
- **Длина допуска на задержку вещания.** Это компромисс между опоздавшими зрителями и числом повторов у накрутчика.
